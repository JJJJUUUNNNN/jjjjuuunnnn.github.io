搭建个人博客时，我使用 Astro、TypeScript 和 MDX，实现了文章标签、目录、全文搜索、评论、主题切换和自动部署。

功能上线之后，我开始检查另一个问题：页面能正常使用，但加载速度和交互细节是否足够好？

这次我用 Lighthouse 检查首页和 MDX 文章页，根据报告完成了两处修改。文章页的性能得分从 97 提升到了复测中的 100，同时修复了一个没有影响总分的无障碍问题。

## 第一步：排除浏览器扩展的干扰

第一次测试首页时，Lighthouse 给出的分数是：

| 检查项 | 得分 |
| --- | --- |
| 性能 | 99 |
| 无障碍 | 100 |
| 最佳实践 | 100 |
| SEO | 100 |

报告还提示存在约 258 KiB 的未使用 JavaScript。

如果只看提示标题，很容易认为博客加载了过多脚本。但查看资源地址后，我发现它来自：

```text
chrome-extension://.../content.js
```

这段脚本属于浏览器扩展，并不是博客代码。报告也明确提示，扩展影响了测试结果。

因此，我先在无痕模式下重新测试，确认报告不再出现扩展干扰警告，再开始分析网站本身的问题。

这一步提醒我：优化前需要确认问题来源，不能看到提示就直接修改代码。

## 第二步：分别检查首页和文章页

首页与文章页的资源组成不同。

首页主要展示个人介绍和文章列表；MDX 文章页还包含封面、交互式计数器和 Giscus 评论。因此，我分别进行了测试。

优化前的无痕模式测试结果如下：

| 指标 | 首页 | MDX 文章页 |
| --- | --- | --- |
| 性能得分 | 99 | 97 |
| 无障碍得分 | 100 | 100 |
| 最佳实践得分 | 100 | 100 |
| SEO 得分 | 100 | 100 |
| FCP | 1.4 秒 | 1.3 秒 |
| LCP | 1.6 秒 | 1.6 秒 |
| TBT | 0 毫秒 | 20 毫秒 |
| CLS | 0 | 0 |
| Speed Index | 2.3 秒 | 4.2 秒 |

其中：

- FCP 表示首批内容出现的时间。
- LCP 表示最大内容元素完成绘制的时间。
- TBT 用于衡量加载过程中的主线程阻塞。
- CLS 用于衡量页面布局的意外偏移。

文章页整体表现已经不错，但报告指出了封面图片和按钮名称两个具体问题。

## 优化一：让封面按实际尺寸加载

原来的文章封面使用 Astro 的 Image 组件：

```astro
<Image
  width={1020}
  height={510}
  src={heroImage}
  alt=""
/>
```

Astro 已经将图片转换成 WebP，报告中的传输大小约为 30 KB。但转换格式并不等于完成了所有图片优化。

Lighthouse 显示，在本次手机测试中，图片实际展示尺寸约为 376 × 188，而下载的图片尺寸是 1020 × 510。

页面缺少可供浏览器选择的图片尺寸，因此窄屏设备也下载了同一份图片。

### 添加响应式候选尺寸

我为组件添加了 widths 和 sizes：

```astro
{
  heroImage && (
    <Image
      src={heroImage}
      width={1020}
      height={510}
      widths={[400, 640, 800, 1020]}
      sizes="(max-width: 1056px) calc(100vw - 2em), 1020px"
      loading="eager"
      fetchpriority="high"
      alt=""
    />
  )
}
```

这里有两个关键属性：

- `widths`：指定构建时生成的图片候选宽度。
- `sizes`：告诉浏览器图片在当前布局中的预计显示宽度。

浏览器可以结合显示宽度和屏幕像素密度选择合适的资源，而不是所有设备都下载同一个尺寸。

`sizes` 需要与实际布局一致。如果以后调整页面宽度或边距，也应该一起检查这项配置。

### 首屏图片不再懒加载

报告还发现，这张封面是本次测试的 LCP 元素，但输出的图片使用了 `loading="lazy"`。

懒加载适合暂时不会出现在视口中的图片。文章封面位于首屏，应该尽早开始加载。

因此，我设置了：

```astro
loading="eager"
fetchpriority="high"
```

前者取消懒加载，后者向浏览器提供较高的加载优先级提示。

这项设置用于文章首屏封面，没有应用到所有图片。正文中位于屏幕下方的图片仍然可以使用懒加载。

关于这些属性，可以参考 [Astro 图片与资源 API](https://docs.astro.build/en/reference/modules/astro-assets/)。

## 优化二：修复计数器按钮的无障碍名称

MDX 文章中有一个计数器，支持加一、减一和重置。

最初的按钮写法是：

```html
<button type="button" data-action="increase" aria-label="加一">
  +1
</button>
```

视觉上，按钮显示的是 `+1`；辅助技术读取的名称则来自 `aria-label`，内容是“加一”。

Lighthouse 指出了两者不匹配的问题：无障碍名称没有包含按钮的可见文字。

### 在名称中保留可见标签

我将两个按钮改为：

```html
<button type="button" data-action="decrease" aria-label="减一（−1）">
  −1
</button>

<button type="button" data-action="increase" aria-label="加一（+1）">
  +1
</button>
```

这样既提供了中文说明，也保留了界面上实际显示的标签。

这个检查项没有影响当次无障碍总分，所以页面即使得到了 100 分，仍然存在值得修复的问题。

对我来说，这是这次验收里很有价值的一点：总分是入口，具体检查结果才是修改依据。

## 哪些提示没有立即处理？

报告还提示了缓存生命周期和渲染阻塞 CSS。我没有继续修改这些部分。

### 静态资源缓存

报告显示，站点字体、图片和 CSS 的缓存时间为 10 分钟。

这是当前托管服务返回的 HTTP 缓存策略。修改 Astro 页面组件不会直接改变这些响应头，本次也没有为此调整托管方案。

### 小型样式文件

报告中的外部 CSS 文件约为 1.5～1.7 KB。

样式参与首屏渲染，但页面当时的 LCP 已经是 1.6 秒。我没有将它改成异步加载，以免增加页面先显示无样式内容的可能。

### 评论组件

文章页的 Speed Index 比首页高，但仅凭这份报告，我无法确认差异是否由 Giscus 导致。

因此，这次没有改动评论加载方式。需要调整时，应先收集能定位原因的证据。

## 验证与发布

修改完成后，我先运行类型检查和生产构建：

```bash
pnpm check
pnpm build
pnpm preview
```

在预览页面中检查：

- 封面显示是否正常。
- 计数器加减和重置是否正常。
- 亮暗主题切换是否正常。

确认通过后，提交代码并通过 GitHub Actions 自动部署，再对线上文章页运行 Lighthouse。

优化前，文章页性能得分为 97；部署后的复测性能得分达到了 100。

这个分数对应一次具体测试，不能保证所有设备、网络环境和后续测试都得到相同结果。后续增加组件或第三方资源时，仍然需要重新检查。

## 这次优化带给我的经验

这次改动不大，但让我建立了一套更明确的检查顺序：

1. 确认测试环境，排除浏览器扩展等干扰。
2. 分别检查资源组成不同的页面。
3. 阅读具体资源和元素信息，定位问题来源。
4. 优先修改证据明确、范围可控的问题。
5. 检查功能，再部署复测。
6. 记录结果与限制，不把一次分数当作永久结论。

博客不仅是发布文章的地方，也可以成为持续验证前端工程实践的项目。

从响应式图片到无障碍标签，这些细节让页面更完善，也让我对已经写下的代码有了更具体的理解。
